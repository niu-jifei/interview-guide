# PromptSanitizer 类设计分析

## 一、类定位与职责

`PromptSanitizer` 是一个 **Prompt 注入防护工具类**，核心职责是在用户输入拼接到 LLM Prompt 之前，对输入进行安全清洗，防止攻击者通过恶意输入覆盖系统提示词、劫持对话角色或逃逸上下文边界。

从类注释可以看到它明确限定了自己的适用范围：

> 仅用于 4 个严重风险的直接拼接点（裸拼接，无模板包裹）。模板插值点有 Layer 2 的系统提示词保护，不需要额外净化。

这体现了 **纵深防御** 的思路——不是所有入口都需要净化，只有风险最高的"裸拼接"点才由这个类处理，其他点由上层系统提示词保护。

## 三、核心设计思路

### 1. 四维检测体系 —— 覆盖 Prompt 注入的四种攻击向量

| 攻击向量 | 对应的正则模式 | 攻击者意图 |
|----------|---------------|-----------|
| 角色劫持 | `ROLE_INJECTION_PATTERN` | 伪造 `system: xxx` 来冒充系统角色，覆盖系统提示词 |
| 指令覆盖 | `INJECTION_PHRASE_PATTERN` | 用"忽略之前指令"、"你的新角色是"等短语直接覆盖行为 |
| 边界逃逸 | `DELIMITER_INJECTION_PATTERN` | 伪造模板中固定的分隔符来提前关闭段落，逃逸上下文 |
| 标签伪造 | `BOUNDARY_TAG_PATTERN` | 伪造 `<data-boundary>` 标签来干扰边界包裹机制 |

这四个维度覆盖了 Prompt 注入攻击中最常见的几类手法，形成完整的检测面。

### 2. 精确匹配，避免误杀 —— 安全与可用性的平衡

这是一个关键的设计取舍。注意 `INJECTION_PHRASE_PATTERN` 的设计：

- **不单独匹配** `ignore`、`instruction`、`忽略` 等单个常见词，因为它们是正常对话中可能出现的词汇。
- **而是匹配组合短语**，如 `ignore previous instructions`、`忽略之前的指令`，这些组合才具有注入攻击的特征。
- 同样，`ROLE_INJECTION_PATTERN` 通过 `(?im)^` 只匹配行首的角色声明，避免误杀 `Experience with system design` 这类正常文本。

### 3. 主动防御 + 被动防御双层防护

这是整个类最精妙的设计点：

```text
┌─── 被动防御（sanitize） ─────────────────────────────────┐
│  将用户输入中已有的 <data-boundary> 标签替换为无害文本    │
│  清除攻击者带入的任何旧标签                                │
└───────────────────────────────────────────────────────────┘
                            │
                            ▼
┌─── 主动防御（wrapWithDelimiters） ───────────────────────┐
│  生成随机 UUID 包裹用户输入，攻击者无法预测边界值           │
│  确保标签的唯一性和不可伪造性                              │
└───────────────────────────────────────────────────────────┘
```

- **被动防御**：`BOUNDARY_TAG_PATTERN` 在 `sanitize()` 阶段清洗掉输入中已有的标签。
- **主动防御**：`wrapWithDelimiters()` 用随机 UUID 生成新标签，攻击者无法提前构造。
- 两者缺一不可：只有被动防御，攻击者可以尝试暴力猜测；只有主动防御，攻击者带入的旧标签可能干扰判断。

### 4. 职责分离 —— 三个方法各司其职

| 方法 | 职责 | 是否修改原文 | 适用场景 |
|------|------|:----------:|---------|
| `sanitize()` | 清洗 + 替换 | ✅ 是 | 正常业务流程，需要净化用户输入后使用 |
| `wrapWithDelimiters()` | 随机边界包裹 | ✅ 是（包裹） | 拼接用户内容到 Prompt 时使用 |
| `detectInjectionAttempt()` | 仅检测，不干预 | ❌ 否 | 安全审计、监控告警，不影响用户 |

这种分离让调用方可以根据场景灵活选择：

- **既要安全又要可用** → `sanitize()` + `wrapWithDelimiters()`
- **只做安全监控不阻断** → `detectInjectionAttempt()`

### 5. 可配置性 —— 通过开关控制

```java
private boolean isSanitizerEnabled() {
    return properties.getAdvisors() == null
        || properties.getAdvisors().isPromptSanitizerEnabled();
}
```

净化器可以通过配置 `app.ai.advisors.promptSanitizerEnabled` 控制启停。这在问题排查或临时降级时非常有用——不需要修改代码，只需要调整配置。

### 6. 日志告警，不阻断用户

在 `sanitize()` 中检测到注入时，只记录 `warn` 日志，不抛出异常或拒绝请求：

```java
if (injected) {
    log.warn("检测到潜在 Prompt 注入尝试，文本长度: {}", text.length());
}
```

这是一个重要的安全体验平衡——误判时不会影响用户正常使用，同时安全团队可以通过日志追溯攻击行为。

## 四、设计模式总结

| 设计原则 | 体现 |
|---------|------|
| 单一职责 | 一个类只做 Prompt 注入防护一件事 |
| 开闭原则 | 新增检测模式只需添加新的 Pattern 常量，无需修改现有逻辑 |
| 纵深防御 | 正则清洗 + 随机边界包裹 + 配置开关，多层防护 |
| 关注点分离 | 检测、清洗、包裹三个方法职责清晰不重叠 |
| 防御性编程 | 空值检查、空白检查、配置开关兜底 |
| 最小权限 | 只匹配组合短语而非单个关键词，避免过度限制 |
